# 10 — Architecture

## Target file layout

```
 api/trexio.py            CORE  (hand-written; ~450–900 lines)
   - from . import _base
   - from ._base import (Error, string_of_error, PYTREXIO_MAX_STR_LENGTH,
                         TREXIO_SUCCESS, TREXIO_FAILURE, TREXIO_UNSAFE_ARRAY_DIM, ...)
   - from ._base import pytr
   - (module-level) File class, _open, _close, flush, _inquire, _cp, info,
     to_bitfield_list, to_orbital_list, to_orbital_list_up_dn,
     convert_nao_radius, evaluate_nao_radial, evaluate_nao_radial_all
   - re-exports the _base constants under the same names (so `trexio.TREXIO_HDF5` etc. still work)
   - AT THE BOTTOM:  from . import trexio_gen   # pulls has_/read_/write_/delete_ into `trexio`
   - __all__ / explicit re-export so the public surface is unchanged

 api/trexio/_base.py      SHARED (small; no circular deps)
   import numpy as np
   from . import pytrexio as pytr        # the compiled low-level module (pytr)
   Error, string_of_error
   TREXIO_FAILURE ... TREXIO_AMBIGUOUS_CARTESIAN   (the module-level code constants)
   TREXIO_HDF5 / TEXT / AUTO / MEMORY / INVALID_BACK_END   (back-end ids — must match installed lib)
   PYTREXIO_MAX_STR_LENGTH

 api/trexio_gen.py        GENERATED (tools/gen_trexio_py.py output; DO NOT HAND-EDIT)
   header banner "GENERATED by tools/gen_trexio_py.py -- DO NOT EDIT BY HAND."
   from . import pytrexio as pytr       # NEVER `from . import trexio` (that is the cycle)
   import numpy as np
   from . import _base                  # for Error / codes / PYTREXIO_MAX_STR_LENGTH / pytr / np
   (then the 862 has_/read_/write_/delete_ functions, bodies per references/20)

 api/trexio/              PACKAGE DIR (symlinks, exactly as today)
   __init__.py    -> ../trexio.py                (unchanged)
   _version.py    -> ../pytrexio/_version.py     (unchanged)
   trexio_gen.py  -> ../trexio_gen.py            (NEW)
   pytrexio.<tag>.so                       (build artifact, gitignored)
```

## The import cycle, and why `_base.py` kills it

If `api/trexio_gen.py` did `from . import pytr, Error, TREXIO_SUCCESS` (i.e. imported from
the package `__init__`), then `api/trexio/__init__.py` doing `from . import trexio_gen`
would be a cycle: `__init__` is still executing (hasn't defined `pytr` yet) when
`trexio_gen` tries to import `pytr` back from it → `ImportError`.

So every name `trexio_gen` needs at import time is pulled from **`_base`** (a plain module
that imports only `numpy` and the `pytr` compiled module — neither of which imports back).
`api/trexio/__init__.py` re-exports those same names from `_base` so the public surface
(`trexio.Error`, `trexio.TREXIO_HDF5`, `trexio.string_of_error`, ...) is **unchanged**.

Rule (enforced by the generator, checked by a linter/greppable invariant): **`api/trexio_gen.py`
must not reference `from . import <name>` where `<name>` is defined in `api/trexio/__init__.py`.**
Its only `from . import …` lines are `pytrexio` and `_base`.

## Public-name flow (what a user sees — must not change)

```
import trexio
trexio.File                     <- core (api/trexio.py)
trexio.Error, trexio.string_of_error, trexio.TREXIO_HDF5, trexio.PYTREXIO_MAX_STR_LENGTH
                                <- _base.py, re-exported via api/trexio/__init__.py
trexio.open?  (note: there is no module-level `open`; opening is via File / trexio.File)
trexio.to_bitfield_list, trexio.to_orbital_list(_up_dn)          <- core
trexio.convert_nao_radius, trexio.evaluate_nao_radial(_all)      <- core
trexio.read_*, trexio.write_*, trexio.has_*, trexio.delete_*     <- trexio_gen (re-exported into trexio)
```

So `import trexio; trexio.read_nucleus_charge(f)` keeps working because `api/trexio/__init__.py`
ends with `from . import trexio_gen` (which binds `read_nucleus_charge` in the `trexio` namespace).

## Packaging (why one new symlink is enough)

- `pyproject.toml`: `wheel.packages = ["api/trexio"]` → scikit-build-core copies the
  `api/trexio/` **directory** into the wheel as `trexio/`, following symlinks. So
  `api/trexio/trexio_gen.py -> ../trexio_gen.py` becomes `trexio/trexio_gen.py` in the wheel.
- `CMakeLists.txt` `add_custom_command(POST_BUILD)` already copies the `.so` into
  `api/trexio/`; we **add** the `gen_trexio_py` custom target (deps: `gen_trexio_py.py`,
  `trex.json`, `required_api.names`, `trexio.h`) and **add** `api/trexio/trexio_gen.py` to
  the `install(FILES …)` for non-wheel installs. `pyproject.toml` needs **no** change.
- `api/trexio_gen.py` is **tracked** like `src/generated_bindings.cpp` (not gitignored).

## Generator design (one model, two emitters)

```
                 ┌──────────────────────────────────────────────┐
 required_api.   │  tools/trexio_api_model.py   (shared)        │  trex.json
 names  ───────►  │  parse_protos(header, names)                │
 trexio.h  ─────► │  locate_group_var(data, var)  (longest grp) │  (dims/kinds)
                 │  classify(name, params, data)  -> Rec(family)│
                 └───────────┬───────────────────────┬──────────┘
            C++ emitter      │                         │      Python emitter
            (gen_binding.py) │   (kept, byte-identical) │     (gen_trexio_py.py, NEW)
                             ▼                            ▼
                   src/generated_bindings.cpp    api/trexio_gen.py
```

- **Shared model** = the classification logic already in `tools/gen_binding.py`
  (`parse_protos`, `locate_group_var`, `classify`, `Rec`, the family table, `SKIP`/`EXTRA`/
  `LOW_DIM_FN`). Factor it out so both emitters use ONE definition → they can't drift.
- **Python emitter** = for each `Rec`, emit the body from `references/20` (one template per
  family; dims resolved from `trex.json` via `locate_group_var`). A `OVERRIDES` dict lets a
  specific name (e.g. `write_basis_r_power`) use a bespoke template instead of the family one.
- **Same inputs, same exit-on-unknown** as `gen_binding.py`, so a new family in a release is
  a `TODO:` halt on *both* the C++ and Python outputs (you won't get a C++ that compiles and
  a Python that lies).
